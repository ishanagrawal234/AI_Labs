TASK 0 -- Understand the Search Problem
========================================

Before implementing any software, the warehouse navigation problem must be
formulated mathematically as a formal search problem P = (S, A, T, s0, G, c).

Formal Problem Formulation Table:
--------------------------------------------------------------------------------
Component           | Your specification
--------------------------------------------------------------------------------
State S             | Coordinate pair (r, c) representing the robot's current 
                    | position on the 2D grid, where 0 <= r < H, 0 <= c < W, 
                    | and grid[r][c] != '#' (the cell is not an obstacle).
                    | 
Actions A           | Set of four orthogonal unit movements:
                    | A = {Up, Down, Left, Right}, corresponding to coordinate 
                    | displacements {(-1, 0), (+1, 0), (0, -1), (0, +1)}.
                    | 
Transition T(s, a)  | Deterministic successor function:
                    | T((r, c), a) = (r + dr, c + dc), defined if and only if 
                    | 0 <= r + dr < H, 0 <= c + dc < W, and 
                    | grid[r + dr][c + dc] != '#'.
                    | 
Initial state s0    | The starting grid location of the robot marked 'S' 
                    | (loading bay). In this warehouse map: s0 = (1, 1).
                    | 
Goal G              | The target grid location marked 'G' (dispatch area).
                    | In this warehouse map: G = {(7, 15)}.
                    | 
Cost c(s, a, s')    | Uniform step cost: c = 1 for every valid movement action.
--------------------------------------------------------------------------------

Questions:
(a) What information is necessary to specify a state?
Only the current 2D spatial coordinate of the robot, represented as a tuple (r, c)
denoting row index and column index. Additional parameters such as robot heading,
orientation, velocity, momentum, battery level, or cargo status are not required
because moves are omnidirectional relative to grid axes, execute instantaneously,
and incur uniform unit cost.

(b) What makes an action invalid?
An action is invalid if the attempted movement would cause the robot to:
1. Cross the warehouse boundary (i.e., r + dr < 0, r + dr >= H, c + dc < 0, or
   c + dc >= W).
2. Collide with a fixed obstacle or shelving unit (i.e., grid[r + dr][c + dc] == '#').

(c) Is this a deterministic search problem?
Yes. The environment is fully deterministic, fully observable, and static. Taking
action 'a' in state 's' transitions the robot to the exact designated adjacent cell
with probability 1.0. There is no actuator slip, sensory noise, or dynamic obstacles.

(d) What would constitute a solution?
A solution is an ordered sequence of valid collision-free actions [a1, a2, ..., ak]
(or equivalently, an ordered sequence of states [s0, s1, ..., sk]) such that each
state transition is valid under T, starting at s0 = (1, 1) and ending at sk in G = (7, 15).
An optimal solution is a sequence that minimizes the total accumulated path cost
sum(c) = k (i.e., the shortest path in terms of steps taken).

Think About It:
Separating problem understanding from implementation prevents premature coding errors.
If the state space, transition rules, and goal conditions are not clearly specified
in mathematical terms, prompt engineering or coding will yield ambiguous or buggy
logic that fails to handle edge cases like closed boundaries or isolated goals.



TASK 1 -- Plan the Agent
========================

Before prompting an LLM to generate implementation code, the software architecture
was designed:

1. State Representation in Python:
   Represented as a 2-tuple of integers: `(row, col)`. Tuples in Python are immutable,
   lightweight, and hashable, allowing them to serve directly as dictionary keys
   (for `g_score`, `parent_map`) and set elements (for `closed_set`, `visited`).

2. Warehouse Representation:
   Represented as a list of strings (`List[str]`), where each string corresponds to a
   row in the grid. Characters identify cell semantics: '#' for obstacles, '.' for
   free cells, 'S' for start, and 'G' for goal.

3. Valid Action Determination:
   Encapsulated in `_get_neighbors(state)`. The function iterates through directional
   offsets: `{"Up": (-1, 0), "Down": (1, 0), "Left": (0, -1), "Right": (0, 1)}`.
   A neighbor `(nr, nc)` is valid if `0 <= nr < height`, `0 <= nc < width`, and
   `grid[nr][nc] != '#'`.

4. Goal Recognition:
   Recognised by testing equality upon state expansion: `if current == self.goal:`.
   In A*, checking the goal upon node expansion (rather than upon neighbor generation)
   guarantees that the shortest path has been found when an admissible heuristic is used.

5. Information Stored in the Frontier:
   The frontier is a priority queue (min-heap via Python's `heapq`). Each entry is a
   3-tuple: `(f_score, counter, state)`.
   - `f_score`: Total evaluation cost f(n) = g(n) + h(n), ordering the heap.
   - `counter`: An incrementing integer that serves as a deterministic tie-breaker,
     preventing Python from comparing coordinate tuples when two states have equal f-scores.
   - `state`: The `(row, col)` coordinate tuple.

6. Final Path Reconstruction:
   A dictionary `parent_map: Dict[Coord, Tuple[Coord, str]]` records the preceding state
   and the action taken to reach each state: `parent_map[child] = (parent, action)`.
   Upon reaching the goal, the path is reconstructed by following parent pointers
   backwards to the start, and then reversing the resulting sequence.

Reporting Specification:
The program returns a structured dictionary containing:
- `found`: Boolean indicating whether a collision-free path exists.
- `path`: Ordered list of coordinates from S to G.
- `actions`: Ordered list of action names ('Right', 'Down', etc.).
- `step_details`: Formatted step-by-step transition records (step, from, action, to).
- `path_length`: Integer number of steps in the solution.
- `states_expanded`: Integer count of nodes popped from the frontier and expanded.



TASK 2 -- Ask an LLM to Generate A*
====================================

Prompt Used:
"I am implementing a simple goal-based search agent in Python.
The environment is a grid represented by an ASCII map. The agent starts at S
and must reach G. The symbols # represent obstacles and . represents free cells.
The agent can move up, down, left, or right, and every movement has cost 1.
Implement A* search.
Use Manhattan distance as the heuristic:
h(n) = |x - xG| + |y - yG|.
The program should:
- represent grid positions as states;
- maintain an appropriate frontier;
- calculate g(n), h(n) and f(n);
- avoid repeatedly expanding the same state;
- reconstruct the path when the goal is reached;
- report the path and its length;
- report the number of states expanded.
Keep the implementation simple and explain the main components of the code."

Assessment of LLM Output:
The LLM produced a clean implementation using `heapq` and `dataclasses`/tuples.
However, inspection revealed two critical engineering considerations:
1. Heap comparison bug: If two nodes had identical f-scores, Python attempted to compare
   the state tuples directly (e.g. `(f, (r1, c1))`). If coordinate pairs were also equal
   or unorderable in custom objects, this would raise a TypeError. A unique monotonic
   counter was required to break ties safely.
2. Goal test placement: The initial LLM prompt response tested the goal when generating
   neighbors. For general A* with heuristics, testing upon expansion (when popped from
   the priority queue) is required to ensure optimality.

TASK 4 -- Inspect the A* Algorithm
==================================

Concept Mapping Table:
--------------------------------------------------------------------------------

--------------------------------------------------------------------------------

Visited states      | `closed_set: Set[Coord]` (lines 90, 93, 95)
Path reconstruction | `_reconstruct_path()` method (lines 182-209)
--------------------------------------------------------------------------------

Detailed Questions:
(a) What data structure is used for the A* frontier?
A binary min-heap implemented via Python's standard `heapq` module over a standard
Python list. Entries are tuples `(f_score, counter, state)`.

(b) How does the program select the next state to expand?
`heapq.heappop(frontier)` extracts the entry with the smallest f-score from the min-heap
in O(log N) time.

(c) Where is the heuristic calculated?
In the `_heuristic(self, state, mode)` method. It is invoked when evaluating the initial
state for the frontier (line 86) and when computing `f_score = tentative_g + h_neighbor`
for each candidate neighbor (line 113).

(d) Does the program explicitly calculate f(n) = g(n) + h(n)?
Yes. Line 114 explicitly evaluates `f_score = tentative_g + h_neighbor`, where
`tentative_g` represents g(n) (cost from start to current plus step cost 1) and
`h_neighbor` represents h(n) (estimated cost to goal).

(e) How does the program prevent unnecessary repeated exploration?
1. Through `closed_set: Set[Coord]`: When a node is popped, the program checks
   `if current in closed_set: continue`. Once processed, it is added to `closed_set`.
2. Through the g-score pruning check: A neighbor is only added to the frontier if
   `tentative_g < g_score.get(neighbor, float('inf'))`, ensuring that nodes are only
   re-enqueued if a strictly cheaper route to that state is discovered.



TASK 5 -- Compare A* with Blind Search
=======================================

Both Breadth-First Search (BFS) and A* Search were executed on the original warehouse map.

Comparison Results:
--------------------------------------------------------------------------------
Measure              | BFS             | A* (Manhattan)
--------------------------------------------------------------------------------
Solution found       | True            | True
Path length          | 40 steps        | 40 steps
States expanded      | 64              | 64
--------------------------------------------------------------------------------

Detailed Questions:
(a) Did both algorithms find a solution?
Yes, both algorithms successfully reached the goal.

(b) Did they find paths of the same length?
Yes, both found optimal paths of exactly 40 steps.

(c) Which algorithm expanded fewer states?
On this specific original warehouse map, both algorithms expanded exactly the same
number of states: 64 states.

(d) Why might A* expand fewer states? Why did it expand 64 here?
Normally, A* expands far fewer states than BFS because the heuristic h(n) acts as a
directional guide, focusing the search cone towards the goal and leaving branches
that lead away from the goal unexpanded. For instance, in Test 4 (Alternative Paths),
A* expanded only 9 states compared to BFS's 17 states.

However, on this specific original warehouse map, both algorithms expanded all 64 free
cells due to the deceptive topology (a classic local minimum / cul-de-sac):
1. The goal G is at (7, 15). The open corridor at row 7 allows the robot to reach
   (7, 13), where the Manhattan heuristic is very small (h = 2), yielding f = 17 + 2 = 19.
2. But the cell (7, 14) is a solid wall ('#'). The only viable opening to reach column 15
   is located all the way back up at row 1 (1, 15).
3. To reach row 1, the robot must backtrack up column 13 to row 3, traverse left to
   column 7, and ascend to (1, 7). At (1, 7), g = 26 and h = 14, yielding f = 40.
4. Because the optimal solution path has a cost of f* = 40, any admissible search
   algorithm is mathematically guaranteed to expand every state whose evaluation score
   f(n) <= 40 before expanding the goal state.
5. In this 64-cell warehouse, every single accessible dead-end cell has f(n) <= 40.
   Consequently, A* was lured into exploring all dead ends before retreating along the
   true solution path, causing it to expand all 64 reachable cells.

Think About It:
A* is not magical; its performance is strictly governed by the information provided
by the heuristic. When the heuristic cannot "see" through extensive walls, it provides
overly optimistic estimates for dead ends near the obstacle, causing the algorithm to
behave like blind search in highly constrained labyrinths.



TASK 6 -- Investigate the Heuristic
===================================

1. Justification of Manhattan Distance:
In this warehouse, movement is strictly restricted to four cardinal directions
(Up, Down, Left, Right) with uniform step cost 1 (no diagonal movements).
In the relaxed problem where all obstacle walls are removed, the minimum number of
unit steps required to travel between (r1, c1) and (r2, c2) is exactly:
    h(n) = |r1 - r2| + |c1 - c2|
Since removing constraints never increases the true path cost, Manhattan distance is
strictly admissible: h(n) <= h*(n). Furthermore, moving to an adjacent cell changes
the Manhattan distance by at most 1, matching the step cost c = 1, which satisfies
the triangle inequality: h(n) <= c(n, a, n') + h(n'). Thus, Manhattan distance is both
admissible and consistent (monotonic).

2. Experimental Investigation of Heuristic Variants:

Results on Original Warehouse Map:
--------------------------------------------------------------------------------
Heuristic            | Found    | Path Length  | States Expanded | Admissible?
--------------------------------------------------------------------------------
Zero (h = 0)         | True     | 40           | 64              | Yes
Euclidean            | True     | 40           | 64              | Yes
Manhattan            | True     | 40           | 64              | Yes
2 x Manhattan        | True     | 40           | 64              | No
--------------------------------------------------------------------------------

Results on Alternative Paths Map (Showing Pruning Dynamics):
--------------------------------------------------------------------------------
Heuristic            | Found    | Path Length  | States Expanded | Admissible?
--------------------------------------------------------------------------------
Zero (h = 0)         | True     | 8            | 17              | Yes
Euclidean            | True     | 8            | 9               | Yes
Manhattan            | True     | 8            | 9               | Yes
2 x Manhattan        | True     | 8            | 9               | No
--------------------------------------------------------------------------------

Analysis of the Three Variations:
1. What happens if the heuristic is replaced by h(n) = 0?
   Setting h(n) = 0 reduces A* to Dijkstra's algorithm (Uniform-Cost Search). Because
   all step costs are 1, this behaves identically to Breadth-First Search. It remains
   admissible and guarantees finding the optimal path, but it is completely uninformed.
   In the Alternative Paths map, it expanded 17 states (exploring both the direct path
   and the bottom detour) compared to 9 for informed heuristics.

2. What happens if the heuristic is replaced by Euclidean distance?
   Euclidean distance h_E(n) = sqrt((r - rG)^2 + (c - cG)^2) represents straight-line
   distance. Because the hypotenuse is shorter than the sum of the orthogonal legs,
   h_E(n) <= h_M(n) <= h*(n). Euclidean distance is therefore admissible, but it is
   "less informed" (strictly weakly dominated by Manhattan distance on a 4-connected grid).
   While it produced the optimal path, in general grid graphs it expands equal to or
   more nodes than Manhattan distance.

3. What happens if the heuristic is multiplied by 2?
   Multiplying the heuristic by 2 produces an inadmissible heuristic (Weighted A* with
   w = 2.0). Since 2 * h(n) frequently exceeds the true remaining distance h*(n),
   admissibility is lost, meaning the theoretical guarantee of optimality is forfeited.
   However, the inflated heuristic makes the search significantly more greedy, heavily
   penalizing exploration of any node heading away from the goal. On open maps, this
   prunes expansions dramatically, but on maps requiring deep detours, it can fail to
   find the shortest route.

Think About It (Admissibility & Aggressiveness):
- Overly optimistic heuristics (e.g. h = 0): Underestimate cost heavily; ensure 100%
  optimality, but result in unguided, spherical expansion waves that waste memory and time.
- Overly aggressive heuristics (e.g. h > h*): Overestimate cost; break admissibility;
  may jump greedily toward dead ends or return suboptimal paths, but run significantly faster
  when approximate solutions are acceptable.

The parsing of the ASCII map into dimensions and coordinates, the neighbor-generation

2. Did you find any bugs or design problems?
Yes:
- Priority Queue Tuple Ordering Bug: The LLM initially pushed `(f_score, state)` directly
  into `heapq`. When multiple candidate nodes had identical f-scores, Python attempted
  to evaluate `state1 < state2`, comparing coordinate tuples. While tuple comparison works

  In A*, testing on generation can accept suboptimal paths if an inconsistent heuristic is
  used. The goal check had to be moved strictly to node expansion (after `heappop`).
- Console Character Encoding on Windows: Print outputs with special characters or unicode
  symbols caused `UnicodeEncodeError` in Windows cp1252 consoles, requiring safe ASCII
  formatting.

SECTION 6 -- Final Reflection
=============================

1. Why is it important to formulate the search problem before writing the search algorithm?
Formulating the problem before writing code establishes the mathematical contract of the
system. By defining states, actions, transition models, and cost functions explicitly,
we separate "what the problem is" from "how the search explores it." Without this
clarity, implementation decisions become tangled with problem assumptions, leading to
incorrect state representations (e.g., storing unnecessary state history in the state
identifier), invalid neighbor transitions, or inappropriate heuristic choices.

2. In what sense is A* an "informed" search algorithm?
A* is informed because it leverages domain-specific knowledge about the problem space
through its heuristic function h(n), which estimates the remaining cost to the goal.
While blind algorithms like BFS or Uniform-Cost Search only know where they have been
(accumulated cost g(n)), A* combines historical cost with future estimated cost
f(n) = g(n) + h(n). This forward-looking evaluation allows A* to focus exploration along
the most promising trajectory rather than radiating outward equally in all directions.

3. Why does the choice of heuristic matter?
The heuristic directly controls the search efficiency and the solution quality. If h(n)
is inadmissible (overestimating cost), A* loses its theoretical guarantee of finding the
shortest path. If h(n) is admissible but uninformative (like h = 0), A* degenerates into
an exhaustive blind search that expends unnecessary computation. A well-designed, consistent
heuristic (such as Manhattan distance on a 4-way grid) provides the maximum possible
informedness while maintaining optimality, pruning the state space effectively.

4. What did the LLM contribute to the engineering process?
The LLM functioned as an efficient software engineering assistant that rapidly translated
high-level algorithmic specifications into working boilerplate code. It handled standard
data structure syntax (e.g., `heapq` and `deque`), drafted path-reconstruction logic,
and accelerated development. Rather than writing repetitive loops from scratch, the
engineer was able to focus on high-level system design, edge-case analysis, and verification.

5. What could go wrong if an engineer simply accepted LLM-generated code without testing it?
Blindly accepting LLM code can lead to subtle, catastrophic algorithmic bugs. An LLM can
generate code that executes without syntax errors and returns a path, yet fails to implement
the correct algorithm: it might test goals prematurely, tie-break inconsistently, handle
cycles incorrectly, or silently return suboptimal routes. In AI engineering, "working output
!= validated algorithm." Rigorous testing against formal invariants and known boundary
cases is essential to ensure that the software actually satisfies its theoretical properties.
